## Why

Primary keys on `vehicles`, `locations`, and `trips` currently use 36-char UUIDs generated by `gen_random_uuid()`. Shorter, URL-safe identifiers improve log readability, reduce payload size, and align with the nanoid convention used by client-facing IDs. Database-side generation is preserved via the `nanoid-postgres` extension so the application never assigns IDs — Postgres still defaults the primary key, keeping existing insert paths unchanged.

## What Changes

- Add the `nanoid-postgres` Postgres extension (https://github.com/viascom/nanoid-postgres) to the database, providing a `nanoid()` SQL function.
- **BREAKING**: Change the `id` primary-key column type on `vehicles`, `locations`, and `trips` from `UUID DEFAULT gen_random_uuid()` to `TEXT DEFAULT nanoid(16)`.
- **BREAKING**: Change the `vehicle_id`, `start_location_id`, and `end_location_id` foreign-key columns on `trips` from `UUID` to `TEXT` to match the new key type.
- Update `tripInputSchema` in `src/backend/types.ts` so `vehicle_id`, `start_location_id`, and `end_location_id` accept 16-char nanoid strings instead of `z.uuid()`.
- Update validators and handlers to treat these IDs as opaque text strings.
- Add a dbmate migration that installs the extension, alters column types, and migrates any existing rows (backfilling UUIDs into 16-char text where needed, or clearing dev data).

## Capabilities

### New Capabilities

(none)

### Modified Capabilities

- `trips-api`: primary-key and foreign-key column types change from UUID to 16-char nanoid generated in Postgres; identifier format requirements in the schema and FK validation paths change accordingly.
- `request-validation`: `tripInputSchema` field types for `vehicle_id`, `start_location_id`, and `end_location_id` change from `z.uuid()` to a 16-char nanoid string format.

## Impact

- **Database**: New migration installs `nanoid-postgres` extension and alters three tables plus FK columns. Existing dev data with UUID values must be backfilled or cleared. Requires human review (schema change).
- **API**: `POST /api/trips` request/response shape is unchanged at the field level, but ID values are now 16-char strings instead of UUIDs. Clients sending UUID-shaped IDs will be rejected.
- **Code**: `src/backend/types.ts`, `src/backend/validators.ts`, `src/backend/handlers.ts` updated to drop UUID assumptions.
- **Dependencies**: `nanoid-postgres` is a Postgres extension, not a JS dependency; no new npm packages are added (stack stays within allowed deps).
- **Rollback**: A down migration reverts columns to `UUID DEFAULT gen_random_uuid()`; application code is reverted via git. Existing nanoid text values cannot be cast back to UUID, so rollback requires clearing dev data or restoring from a pre-migration backup.
